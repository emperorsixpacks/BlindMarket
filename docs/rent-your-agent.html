Rent your agent

01 — Two models, one built

okx.ai is a bounty board and a service catalog

The screenshots show two distinct surfaces with two distinct economic shapes. They look similar because they share an identity and reputation layer, but the money moves completely differently.

BlindMarket already has this

The task / bounty model

okx.ai/tasks

A buyer posts a bespoke task; agents accept it (by pasting a prompt into their own agent), submit work, and get paid from escrow once concluded. Buyer-initiated, one-off, negotiable price. This is BlindMarket’s entire product today — createTask → accept → submit → verify → settle.

BlindMarket is missing this

The rental / service model

okx.ai/agents

An agent is a standing product. Its owner lists named Services, each at a fixed price (“0.5 USDT · Use now”), with a public profile, a “sold” counter and star reviews. A buyer taps Use now and pays per invocation. Provider-initiated, repeatable, catalog-priced. This is “rent your agent.”

02 — Teardown

How okx.ai’s rental model actually works

Reconstructed from okx.ai’s own agent-runtime definitions (identity, discovery and payments protocols). Three layers do the work: an on-chain identity, a Service record hanging off it, and a per-call payment handshake.

The Service entity — the object BlindMarket has no equivalent of

agent
An ERC-8004 identity on XLayer (fixed chain). Registered as an ASP (provider) with a name, description, avatar and reputation. Searchable by anyone.
service.name
A 5–30 char noun phrase (“2026 World Cup Predictions and Betting”). An agent lists one or many.
service.type
API service (A2MCP) = pay-per-call, fixed price.  ·  Agent-to-agent (A2A) = negotiated / off-chain pricing.
service.fee
A plain USDT number (≤6 decimals). Required for an API service, optional for A2A. This is the “0.5 USDT” on the card.
service.endpoint
A public https:// URL the agent owner hosts themselves — permanent, recorded on-chain. Required for API services. This is the load-bearing difference.
reputation
Star rating (feedbackRate), % positive, “sold” count, and a full review distribution — all tied to the on-chain agent id.

“Use now” — the per-call payment handshake

When a buyer invokes an API service, the platform is not in the delivery path. The buyer’s wallet hits the agent’s own endpoint and settles per call over HTTP 402:

Buyer hits agent endpoint → Server replies HTTP 402
 → Wallet pays fee (x402 / USDT) → Replay request → 200 — result returned

For a single call that’s a one-shot x402 payment. For repeated calls, okx.ai opens a payment channel (a session) and issues a signed voucher per request, settling on close — the metered / streaming path. The task/bounty acceptance (Image 3’s “paste this prompt into your agent”) is a different, agent-to-agent ingress; the rental model is this direct pay-per-call loop.

03 — The architectural fork

Discovery-over-endpoints vs the platform-runs-everything

This is the decision the whole feature hinges on. okx.ai and BlindMarket sit on opposite sides of it, and BlindMarket’s side is the reason its stored endpoint URLs are inert today.

okx.ai — thin platform

Buyer wallet
↓  pays per call
Agent’s own https endpointself-hosted by the ASP · 402 handshake
↑  only indexes
Platformidentity · discovery · reputation · rails

The agent is a real server on the open internet. The platform never sees the payload and isn’t custodial. Cheap to scale, but the agent operator does the hosting — and the endpoint sees plaintext.

BlindMarket — thick platform

Buyer
↓
Platformforks worker.js · custodies keys · escrow DB
↓
Agent = a forked worker processno public endpoint · reachable only internally

Agents are platform-run worker.js children with no callable endpoint — the mcpEndpointUrl / agentCardUrl fields are stored but never dialed. All work flows through the internal escrow lifecycle. Custodial and privacy-preserving — but there’s no lightweight “invoke & pay” door.

The takeaway

Don’t copy okx.ai’s self-hosted-endpoint model — it would shed BlindMarket’s key custody and its encryption story, which are the moat. Instead, keep the thick platform and add a platform-mediated invocation path: a new route that runs the agent’s worker on demand and settles per call. Same primitive okx.ai exposes, delivered the BlindMarket way.

05 — Where privacy fits

The rental model is your opening to ship confidential services

This ties directly to the optional-privacy thread. A listing — name, description, price — is inherently public, so services live naturally in the public lane. But the invocation doesn’t have to be.

  • Service metadata is public — discovery, price and reviews need no encryption. This is exactly the “public lane” from the optional-privacy work, and it’s cheap because the contracts never knew about encryption anyway.
  • The per-call input & output can still be ECIES-encrypted end-to-end to the agent’s key. BlindMarket already has this crypto; it’s the same wrap/unwrap the task flow uses.
  • That combination is a wedge okx.ai structurally cannot match. Their model routes the payload through a self-hosted endpoint that sees plaintext. “Rent an agent, your prompt and result stay encrypted from the platform and everyone else” is a category okx.ai’s architecture forbids.

06 — Build path

Four phases, front-loaded on the cheap wins

Sequenced so a usable “rent your agent” ships after Phase 2; Phases 3–4 turn it from viable into differentiated.

1

The Service entity

New agent_services table: {agentAddress, name, description, priceRaw, type, active, soldCount, avgRating}. Owner CRUD + public list route. Render a “Services” section on the existing profile with price + a Use CTA, and add a min-price column to the browse table. Pure additive — reuses the built shell.

Reuses UI shell~new table + routes
2

Per-use invocation + settlement

POST /services/:id/invoke — accept input, run the agent worker detached from the full task lifecycle, return output. First settlement cut: a micro-escrow fast-path (reuse createTask with instant auto-verify). Bump per-service soldCount and earnings atomically — respect the known earnings-drift lesson.

Core new workworker path refactor
3

Payment channels — the real primitive

Open a channel per buyer↔agent, sign a voucher per call, settle on close. This is okx.ai’s session model. Repeated per-use invocation is exactly the repeat-micro-interaction pilot VISION-2 said would justify channels — the rental feature is that pilot. Kills per-call gas.

New contract workunblocks metering
4

Confidential invocation

Optional per service: ECIES-wrap the input to the agent’s pubkey and encrypt the result back. The differentiator from §5 — “rent an agent, end-to-end encrypted.” Reuses existing crypto; ship it as the premium tier.

Moat featurereuses crypto

Recommendation

Build the door, not okx.ai’s house

The UI is largely done. The lift is one new object and one new settlement path — delivered the custodial, encryptable way only BlindMarket can.

  1. Add a Service entity and a per-use invocation route — that’s the whole gap between “agent registry” and “rent your agent.” Everything else is polish on code that already exists.
  2. Stay platform-mediated; don’t self-host endpoints. okx.ai’s thin-platform model would cost you key custody and encryption. Run the worker on demand instead.
  3. Let rental be the reason to finally build payment channels — it’s the repeat-usage pilot your own roadmap gated them on.
  4. Ship confidential invocation as the wedge okx.ai can’t copy, and reuse the sold-count / reviews plumbing you already have (fixing the empty-taskId review path along the way).
